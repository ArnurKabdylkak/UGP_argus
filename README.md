# UDPR — UDP + Reliable Transport для дата-диода

UDP используется только как переносчик, гарантии доставки даёт собственный
минимальный протокол поверх него (seq, окно, ACK base + bitmap, CRC, retransmit).
TCP-стек не реализуется — решается ровно задача дата-диода: доставка данных
A → B плюс строго ограниченный обратный ACK-канал.

Консольное приложение на Go: один статический бинарь без зависимостей,
который заворачивает произвольный поток байт в UDPR и доставляет его в точку
назначения.

## Быстрый старт

```bash
go build -o udpr ./cmd/udpr
```

Постоянный приём (устройство B, штатный режим шлюза):

```bash
./udpr serve -bind 0.0.0.0 -port 5555 -dir ./inbox
```

Слушает непрерывно, принимает сессии последовательно и параллельно, каждый
поток кладёт отдельным файлом `<timestamp>-<session>.bin`, переживает разрывы
и перезапуск отправителей. Останавливается по SIGINT/SIGTERM.

Одноразовый приём (принять один поток и выйти — для отладки и разовых передач):

```bash
./udpr recv -bind 0.0.0.0 -port 5555 -out received.bin
```

Отправка (устройство A):

```bash
./udpr send -host 10.0.0.2 -port 5555 -file data.bin
```

Через stdin/stdout, потоком:

```bash
tar cz /var/log | ./udpr send -host 10.0.0.2 -port 5555
```

Локальная проверка с имитацией потерь (сверяет SHA-256 исходного и принятого потока):

```bash
./udpr selftest -size 1000000 -loss 0.2
```

Тесты:

```bash
go test ./... -race
```

Полный список флагов, переменных окружения и кодов возврата —
[docs/cli.md](docs/cli.md).

## Как это работает

Заголовок фиксированной длины **28 байт**, big-endian, за ним payload:

| Поле | Байты | Назначение |
|---|---|---|
| `version` | 1 | версия формата (сейчас 1) |
| `type` | 1 | `HELLO`=1, `DATA`=2, `ACK`=3, `FIN`=4 |
| `flags` | 1 | зарезервировано, в ACK обязан быть 0 |
| `reserved` | 1 | выравнивание |
| `session_id` | 4 | идентификатор потока |
| `sequence` | 4 | номер пакета |
| `length` | 2 | длина payload |
| `window` | 2 | окно отправителя |
| `ack_base` | 4 | первый ещё **не** полученный seq |
| `ack_bitmap` | 4 | биты 0..31 — получен ли seq = `ack_base+1+i` |
| `crc32` | 4 | CRC32 по заголовку (с обнулённым CRC) и payload |

* **Отправитель** держит скользящее окно от `base` (первого неподтверждённого
  seq) и буферизует каждый пакет до подтверждения. Окно считается от `base`, а
  не от числа буферизованных пакетов — иначе выборочно подтверждённые seq
  позволили бы уйти за окно приёма.
* **Приёмник** собирает reorder-буфер и отдаёт наверх только непрерывный
  префикс потока: данные никогда не выходят с дырками и не выходят вне порядка.
* **ACK агрегируется**: раз в 8 пакетов, но не реже 2 мс; разрыв
  последовательности и дубликат подтверждаются немедленно. Подтверждение на
  каждый пакет упирается в лимит частоты ACK Guard и режет пропускную
  способность примерно в 30 раз.
* **Retransmit** по таймауту `-rto` и быстрый повтор при дырке ниже уже
  подтверждённого пакета (не чаще одного раза за `rto/2`).
* **Завершение** по `FIN`; поток закрывается, когда доставлено всё до него.

Подробности, диаграммы состояний и тест-векторы — [docs/protocol.md](docs/protocol.md).

## ACK Guard — контроль обратного канала

Обратный канал управляемый, а не свободный. `internal/domain/ackguard.go`
отклоняет всё, что не является строго детерминированной служебной структурой:
не-ACK пакет, чужой `session_id`, любой payload в ACK, ненулевые `flags`,
`ack_base` вне текущего окна, превышение лимита частоты. Неизвестный `type`,
чужая версия и битый CRC отбрасываются ещё при разборе.

Пакет подтверждения всегда занимает ровно 28 байт и не несёт полезной
нагрузки — обратный поток проверяем по размеру на уровне оборудования.
Счётчик отклонений и последняя причина печатаются по завершении передачи.

## Постоянный адрес обратного канала

По умолчанию ОС выдаёт отправителю эфемерный локальный порт, и он меняется при
каждом запуске: обратный ACK-поток каждый раз приходит на новый порт, и описать
его постоянным правилом невозможно. `-lport` закрепляет порт, и обратный канал
получает неизменный 5-tuple:

```bash
./udpr send -host 10.0.0.2 -port 5555 -lport 5556 -file data.bin
```

Если порт занят, запуск завершается понятной ошибкой, а не тихим переходом
на эфемерный.

## Производительность

Loopback, один поток, обычные сокеты ядра (Go), `-rto 20ms`, 200 МБ:

| Конфигурация | Время | Пропускная способность |
|---|---|---|
| ACK на каждый пакет, лимит 5000 ACK/с | 33,0 с | ~6 МБ/с |
| агрегированный ACK, лимит 20000 ACK/с | 1,1 с | ~180 МБ/с (≈1,5 Гбит/с) |

Потолок задаёт частота ACK, а не сокеты: `AckRate × AckEvery × MTU`. Прежде чем
менять транспорт, проверяйте эти три параметра.

Горячий путь не аллоцирует: окно отправителя и буфер пересборки — кольца
фиксированного размера, ACK уходят через переиспользуемый буфер, CRC считается
без копии пакета (`go test ./internal/domain -bench . -benchmem`).

## Сессии и отказы

`serve` ведёт таблицу сессий с ключом «источник + `session_id`»: два потока с
одинаковым `session_id` от разных адресов не смешиваются. Сессия закрывается по
`FIN` (**ЗАВЕРШЕНА**) либо выселяется, если замолчала дольше `-idle`
(**ПРЕРВАНА**). Разница принципиальная: прерванная сессия — это потерянные
данные, и она обязана быть видна в логе и в счётчике `evicted`. Диод, который
молча перестал доставлять, — худший из возможных отказов.

## Структура

Чистая архитектура, зависимости направлены внутрь: `domain` не знает никого,
`usecase` знает `domain` и `port`, `adapter` реализует `port`, и лишь `app`
знает всех. В `main` не остаётся ничего, кроме вызова `app.Run`.

```
internal/domain/   ядро протокола: без сети, файлов и системных часов
internal/port/     границы наружу: Link, Clock, SinkFactory
internal/usecase/  сценарии: Sender, Server, Receiver
internal/adapter/  реализации портов: udplink, lossylink, sysclock, filesink
internal/app/      точка сборки: CLI, флаги, окружение, логи
cmd/udpr/main.go   только os.Exit(app.Run(os.Args[1:]))
```

Смена инкапсуляции (свой IP-протокол, L2 поверх прямого линка) — это новая
реализация `port.Link`, а не правка протокола; другое назначение потока
(очередь, форвардер в SIEM вместо файла) — новая реализация
`port.SinkFactory`. Логика доставки в обоих случаях не меняется.

Подробнее — [docs/architecture.md](docs/architecture.md).

## Ограничения

* Нет аутентификации и шифрования: CRC32 защищает от искажений в канале, но не
  от активной подмены. Криптозащиту нужно добавлять отдельным слоем.
* `sequence` 32-битный, без wraparound — потока хватает на ~5,9 ТБ при MTU 1372.
* Окно ограничено 32 пакетами разрядностью ACK bitmap: на каналах с большой
  задержкой это ограничит скорость.
* RTO фиксированный, без адаптивной оценки RTT.
* Нет управления перегрузкой и определения MTU пути.
* На конечных узлах требуется этот агент — совместимости с обычными
  TCP-приложениями нет по построению.
