# UDPR — UDP + Reliable Transport для дата-диода

UDP используется только как переносчик, гарантии доставки даёт собственный
минимальный протокол поверх него (seq, окно, ACK base + bitmap, CRC, retransmit).
TCP-стек не реализуется — решается ровно задача дата-диода: доставка данных
A → B плюс строго ограниченный обратный ACK-канал.

Консольное приложение на Go: один статический бинарь без зависимостей,
который заворачивает произвольный поток байт в UDPR и доставляет его в точку
назначения.

## Сборка и запуск

```bash
go build -o udpr ./cmd/udpr
```

Постоянный приём (устройство B, штатный режим шлюза):

```bash
./udpr serve -bind 0.0.0.0 -port 5555 -dir ./inbox
```

Слушает непрерывно, принимает сессии последовательно и параллельно, каждый
поток кладёт отдельным файлом `<timestamp>-<session>.bin`, переживает разрывы
и перезапуск отправителей. Останавливается по SIGINT/SIGTERM.

Одноразовый приём (принять один поток и выйти — для отладки и разовых передач):

```bash
./udpr recv -bind 0.0.0.0 -port 5555 -out received.bin
```

Отправка (устройство A):

```bash
./udpr send -host 10.0.0.2 -port 5555 -file data.bin
```

Через stdin/stdout, потоком:

```bash
tar cz /var/log | ./udpr send -host 10.0.0.2 -port 5555
```

Локальная проверка с имитацией потерь (сверяет SHA-256 исходного и принятого потока):

```bash
./udpr selftest -size 1000000 -loss 0.2
```

Тесты:

```bash
go test ./... -race
```

## Формат пакета

Заголовок фиксированной длины **28 байт**, big-endian, за ним payload:

| Поле | Байты | Назначение |
|---|---|---|
| `version` | 1 | версия формата (сейчас 1) |
| `type` | 1 | `HELLO`=1, `DATA`=2, `ACK`=3, `FIN`=4 |
| `flags` | 1 | зарезервировано, в ACK обязан быть 0 |
| `reserved` | 1 | выравнивание |
| `session_id` | 4 | идентификатор потока |
| `sequence` | 4 | номер пакета |
| `length` | 2 | длина payload |
| `window` | 2 | окно/лимит |
| `ack_base` | 4 | первый ещё **не** полученный seq |
| `ack_bitmap` | 4 | биты 0..31 — получен ли seq = `ack_base+1+i` |
| `crc32` | 4 | CRC32 по заголовку (с обнулённым CRC) и payload |

`MTU` payload по умолчанию 1372 байта (1400 − 28), чтобы пакет укладывался
в типовой Ethernet MTU без фрагментации.

## Механика доставки

* **Отправитель** держит скользящее окно от `base` (первого неподтверждённого seq)
  и буферизует каждый пакет до подтверждения.
* **Приёмник** собирает reorder-буфер, отдаёт наверх только непрерывный префикс
  потока и на каждый DATA отвечает ACK `(base, bitmap)`.
* **ACK агрегируется**: подтверждение раз в `AckEvery` пакетов (по умолчанию 8),
  но не реже `AckDelay` (2 мс); разрыв последовательности и дубликат
  подтверждаются немедленно. Подтверждение на каждый пакет упирается в rate
  limit ACK Guard и режет пропускную способность примерно в 30 раз.
* **Retransmit** по таймауту `-rto` и fast retransmit при дырке ниже уже
  подтверждённого пакета (не чаще одного повтора за `rto/2`).
* **Завершение**: `FIN` с номером последнего seq; приёмник закрывает поток,
  когда доставил всё до `FIN`, либо по `-idle`.

Окно считается от `base`, а не от числа буферизованных пакетов — иначе выборочно
подтверждённые seq позволили бы отправителю уйти за окно приёма.

## Постоянный адрес обратного канала

По умолчанию ОС выдаёт отправителю эфемерный локальный порт, и он меняется при
каждом запуске. Тогда обратный ACK-поток каждый раз приходит на новый порт, и
описать его постоянным правилом невозможно — пришлось бы открывать весь
эфемерный диапазон.

`-lport` закрепляет порт, и обратный канал получает неизменный 5-tuple:

```bash
./udpr send -host 10.0.0.2 -port 5555 -lport 5556 -file data.bin
```

Отправитель печатает фактический адрес сокета — тот, на который придут ACK:

```
[send] 10.0.0.1:5556 -> 10.0.0.2:5555, сессия 4eb9dfef
```

Если порт занят, запуск завершается понятной ошибкой, а не тихим переходом
на эфемерный.

## ACK Guard — контроль обратного канала

Обратный канал управляемый, а не свободный (слайд 15). `internal/domain/ackguard.go`
отклоняет всё, что не является строго детерминированной служебной структурой:

* не-ACK пакет в обратном канале;
* чужой `session_id`;
* любой payload в ACK;
* ненулевые `flags`;
* `ack_base` вне текущего окна `[base, next_seq]`;
* превышение лимита частоты ACK (token bucket, по умолчанию 5000 ACK/с, burst 256);
* неизвестный `type`, чужая версия и битый CRC — отбрасываются ещё в `Decode`.

Счётчик отклонений и последняя причина печатаются по завершении передачи.

## Производительность

Loopback, один поток, обычные сокеты ядра (Go), `-rto 20ms`, 200 МБ:

| Конфигурация | Время | Пропускная способность |
|---|---|---|
| ACK на каждый пакет, лимит 5000 ACK/с | 33.0 с | ~6 МБ/с |
| агрегированный ACK, лимит 20000 ACK/с | 1.0 с | ~200 МБ/с (≈1.6 Гбит/с, 144k pps) |

Потолок задаёт частота ACK, а не сокеты: `AckRate × AckEvery × MTU`. Прежде чем
менять транспорт, проверяйте эти три параметра.

## Флаги

| Флаг | Команда | По умолчанию | Назначение |
|---|---|---|---|
| `-host`, `-port` | send | — / 5555 | адрес получателя |
| `-bind`, `-port` | recv | 0.0.0.0 / 5555 | адрес прослушивания |
| `-file` / `-out` | send / recv | `-` | файл или stdin/stdout |
| `-mtu` | send | 1372 | payload на пакет |
| `-window` | обе | 32 | размер окна в пакетах (≤ 32 — предел bitmap) |
| `-rto` | send | 250ms | таймаут повторной отправки |
| `-lport` / `-laddr` | send | эфемерный | фиксированный локальный порт/адрес отправителя |
| `-dir` | serve | — | каталог для принятых потоков |
| `-idle` | recv / serve | 10s / 60s | выход после тишины / выселение сессии |
| `-max` | serve | 64 | предел одновременных сессий |
| `-loss` | все | 0 | имитация потерь канала для тестов |
| `-v` | все | false | подробный лог |

На канале с реальными потерями и низким RTT стоит уменьшить `-rto`: на loopback
с 10% потерь переход с 250 ms на 40 ms сократил передачу 500 КБ с 3.8 с до 0.5 с.

## Структура

Слои чистой архитектуры, зависимости направлены только внутрь: `domain` не знает
никого, `usecase` знает `domain` и `port`, `adapter` реализует `port`, и лишь
`app` знает всех — там разбирается командная строка и собирается граф
зависимостей. В `main` не остаётся ничего, кроме вызова `app.Run`.

```
internal/domain/       ядро протокола: без сети, файлов и системных часов
  packet.go            формат и разбор пакета, CRC
  window.go            окно отправителя, таймауты, fast retransmit
  reassembly.go        контроль seq, reorder-буфер, ACK bitmap
  ackguard.go          политика обратного канала

internal/port/         границы наружу: Link, Clock, SinkFactory
  port.go

internal/usecase/      сценарии поверх домена и портов
  sender.go            передача потока: очередь, ACK, повторы
  server.go            постоянный приём, таблица сессий, выселение
  session.go           политика ACK для одной сессии
  receiver.go          одноразовый приём (обёртка над Server)

internal/adapter/      реализации портов
  udplink/             port.Link поверх UDP-сокета
  lossylink/           обёртка Link с имитацией потерь (для тестов и -loss)
  sysclock/            port.Clock поверх системных часов
  filesink/            port.SinkFactory: сессия -> файл в каталоге

internal/app/          точка сборки: CLI и связывание адаптеров со сценариями
  app.go               Run: разбор команды, коды возврата, usage
  wire.go              создание адаптеров под сценарий
  send.go recv.go serve.go selftest.go   флаги и запуск команд
  io.go                stdin/stdout, файлы, предупреждения

cmd/udpr/main.go       только os.Exit(app.Run(os.Args[1:]))
```

Практический смысл границ: смена инкапсуляции (свой IP-протокол, L2 поверх
прямого линка) — это новая реализация `port.Link`, а не правка протокола;
другое назначение потока (очередь, форвардер в SIEM вместо файла) — новая
реализация `port.SinkFactory`. Логика доставки в обоих случаях не меняется.

## Сессии и отказы

`serve` ведёт таблицу сессий с ключом «источник + `session_id`»: два потока с
одинаковым `session_id` от разных адресов не смешиваются. Сессия закрывается по
`FIN` (**ЗАВЕРШЕНА**) либо выселяется, если замолчала дольше `-idle`
(**ПРЕРВАНА**). Разница принципиальная: прерванная сессия — это потерянные
данные, и она обязана быть видна в логе и в счётчике `evicted`. Диод, который
молча перестал доставлять, — худший из возможных отказов.

## Ограничения MVP
* `sequence` 32-битный, без wraparound — потока хватает на ~5.9 ТБ при MTU 1372.
* Нет аутентификации и шифрования: целостность проверяется CRC32, что защищает
  от искажений в канале, но не от активного подмены. Криптозащиту нужно
  добавлять отдельным слоем.
* RTO фиксированный, без адаптивной оценки RTT.
* На конечных узлах требуется этот агент — совместимости с обычными
  TCP-приложениями нет по построению (см. минусы варианта 2 на слайде 12).
